# OCR Result To Customs Site Submission Design

## Background

The current system extracts structured OCR results from uploaded documents and shows them in the result center. The next capability is to let the operator review those results, adjust them, and then manually trigger a server-side headless browser submission into `https://vatest.carsem.com.cn/`.

The target site is an ASP.NET MVC application. As of March 15, 2026, the test site login page is `https://vatest.carsem.com.cn/Home/Login`, and after login it lands on a single "数据录入" page with a form posted to `/Home/SaveData`.

## Goal

Add a safe review-and-submit workflow that:

1. Keeps the current OCR extraction flow unchanged.
2. Builds a customs-site submission draft from OCR output.
3. Lets the user review and edit that draft in the result center.
4. Uses a backend headless browser to log in and submit the reviewed draft to the customs site on demand.
5. Stores submission status and logs on the history record for later auditing.

## Non-Goals

- No automatic submission immediately after OCR.
- No replacement of the existing OCR `detected` result shape.
- No support for multiple customs sites in the first iteration.
- No attempt to infer every mapping perfectly without review.

## Current Context

### Existing OCR flow

- Backend endpoint `/api/extract` performs MinerU extraction and LLM-based structured extraction.
- Backend endpoint `/api/extract/submit` queues the extraction as an async task.
- Extraction responses are persisted under `output/history/<record_id>/meta.json`.
- Result center already loads the latest task result and history detail.

### Target customs site fields

The target "数据录入" page currently contains:

Header fields:

- `DeclarationNo` (readonly, generated by site)
- `MainBLNo`
- `SubBLNo`
- `CustomerName`
- `TradeType`
- `OriginCountry`
- `InvoiceNo`
- `Quantity`
- `GrossWeight`
- `NetWeight`
- `TotalSheets`
- `TotalQuantity`
- `GoodQuantity`
- `TotalPrice`

Detail row fields:

- `ItemCode`
- `ItemOrigin`
- `ItemQuantity`
- `ItemGoodQuantity`
- `ItemPrice`
- `ItemUnitPrice`

The page adds detail rows dynamically and submits the serialized form to `/Home/SaveData`.

## Recommended Approach

Use a three-layer review model:

1. OCR extraction result remains the source extraction artifact.
2. A derived `submission` draft is generated from OCR result plus mapping rules.
3. The user reviews and edits the draft before clicking a manual submit button.

This balances speed and safety. Pure auto-submit is too risky because OCR field names do not naturally match the customs-site schema, and several site fields are required.

## Proposed Data Model

Add a new `submission` object alongside the stored extraction response payload.

```json
{
  "submission": {
    "target": "vatest.carsem.com.cn",
    "header": {
      "MainBLNo": "",
      "SubBLNo": "",
      "CustomerName": "",
      "TradeType": "",
      "OriginCountry": "",
      "InvoiceNo": "",
      "Quantity": "",
      "GrossWeight": "",
      "NetWeight": "",
      "TotalSheets": "",
      "TotalQuantity": "",
      "GoodQuantity": "",
      "TotalPrice": ""
    },
    "details": [
      {
        "ItemCode": "",
        "ItemOrigin": "",
        "ItemQuantity": "",
        "ItemGoodQuantity": "",
        "ItemPrice": "",
        "ItemUnitPrice": ""
      }
    ],
    "meta": {
      "required_missing": [],
      "unmapped_fields": [],
      "auto_mapped": {},
      "last_edited_at": "",
      "submit_status": "idle",
      "submit_message": "",
      "submit_result": null
    }
  }
}
```

### Why separate `submission` from `detected`

- OCR output remains inspectable and unchanged.
- Site-specific reshaping stays isolated from extraction logic.
- User edits can be tracked without rewriting the OCR payload.
- Future target sites can reuse the same pattern.

## Mapping Strategy

Use a hybrid mapping strategy with user confirmation.

### Layer 1: explicit template mapping

Each OCR template can optionally define mappings from OCR fields to customs-site fields.

Examples:

- `主提单号 -> MainBLNo`
- `客户名称 -> CustomerName`
- `商品明细[].料号 -> details[].ItemCode`
- `商品明细[].总价 -> details[].ItemPrice`

### Layer 2: alias-based fallback mapping

If explicit mapping is absent, use alias matching for common synonyms.

Examples:

- `主提运单号`, `主提单号`, `主单号` -> `MainBLNo`
- `客户`, `收货客户`, `客户名称` -> `CustomerName`
- `总价`, `货值`, `金额` -> `TotalPrice`
- `料号`, `商品编码`, `商品料号` -> `ItemCode`

### Layer 3: manual correction

The result center shows the generated draft and lets the operator edit values before submission.

This is the final safety gate and is mandatory for the first release.

## UX Design

Extend the existing result center with a new "报关填报预览" panel.

### New result-center areas

- OCR result overview: existing extracted fields remain visible.
- Submission draft panel: site-shaped payload for the customs system.
- Validation summary: required missing fields, unmapped OCR fields, and item counts.
- Submission controls: "保存草稿" and "执行填报".
- Submission history/status: current state, last attempt time, result message, returned declaration number if available.

### Draft editing behavior

- Header fields are editable inline.
- Detail rows are editable inline.
- Rows can be added and removed before submit.
- Missing required fields are highlighted.
- Unmapped OCR fields are shown separately so no extracted information disappears silently.

### Button behavior

- `保存草稿`: persists user edits into the history record.
- `执行填报`: validates the draft, then starts a dedicated submission task.
- Disable `执行填报` while a submission is in progress.
- Block duplicate submission by default once a record is marked successful.

## Backend Design

### New responsibilities

1. Draft construction
2. Draft persistence
3. Submission validation
4. Headless browser execution
5. Submission status tracking

### API additions

Recommended new endpoints:

- `POST /api/history/{record_id}/submission-draft`
  - Generate or regenerate a draft from OCR response and mapping rules.
- `PUT /api/history/{record_id}/submission-draft`
  - Save user-edited draft content.
- `POST /api/history/{record_id}/submit-customs`
  - Start an async submission task using the saved draft.
- `GET /api/customs-submit/tasks`
  - List submission tasks.
- `GET /api/customs-submit/tasks/{task_id}`
  - Read a submission task status.

### Persistence

Store the `submission` object inside the history record `response` payload so it stays colocated with the OCR result it was derived from.

Also persist a task-oriented submission log, including:

- login URL used
- submission start/end time
- site response message
- generated `DeclarationNo` if captured
- sanitized browser step trace
- failure reason if any

## Headless Browser Design

Use Playwright on the backend.

### Submission flow

1. Open `https://vatest.carsem.com.cn/Home/Login`
2. Log in with configured credentials.
3. Wait for the "数据录入" page.
4. Fill header fields.
5. Add and fill detail rows one by one.
6. Submit the form.
7. Capture success/failure alert text and post-submit page state.
8. Record returned declaration number if visible.

### Error handling

Return structured failure categories:

- `validation_error`
- `login_failed`
- `page_structure_changed`
- `submission_rejected`
- `network_error`
- `unexpected_error`

Each category should include a concise user-facing message and a more detailed operator log.

### Credentials

Credentials should not be hardcoded in the UI. They should live in backend settings or environment variables, even if the first deployment uses the currently supplied test account.

## Validation Rules

Before browser submission:

- Ensure all required header fields are present except the site-generated `DeclarationNo`.
- Ensure at least one detail row exists.
- Ensure every detail row has all required fields.
- Normalize numeric fields to strings/numbers acceptable by the target form.
- Reject empty-string detail rows.

## Risks And Mitigations

### Risk: OCR fields do not map cleanly

Mitigation: keep explicit template mapping plus a human review step.

### Risk: site DOM changes

Mitigation: use stable selectors where possible, centralize browser selectors, and return a `page_structure_changed` error when fields are missing.

### Risk: duplicate submissions

Mitigation: lock successful records from accidental resubmission unless the user explicitly requests a retry.

### Risk: credentials leakage

Mitigation: keep credentials server-side only and never echo them back to the frontend.
